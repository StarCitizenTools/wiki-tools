# Module:Entity/Location

Location kind: entities backed by the game-data `/api/locations` endpoint (star systems, jump points, stars, planets, moons and asteroid formations). Five leaves render it, StarSystem, JumpPoint, Star, Body and Belt; every other location type stays unclaimed until a leaf exists for it.

Editors never invoke this module directly; it runs inside [Template:Location](https://starcitizen.tools/Template:Location), which declares the kind, or inside [Template:Entity](https://starcitizen.tools/Template:Entity) when the page's uuid resolves to a location record the kind claims; the pipeline and the hook table are on [Module:Entity](https://starcitizen.tools/Module:Entity).

## For module editors

### API

- `p.name = 'Location'`: canonical kind name, exposed as `Data.get(args).kind`.
- `p.editorialMode = true`: a kind-declared page (`{{Location}}` injects `|kind=Location`) with no genuine record renders through the editorial fork, the entry path for lore systems that exist only in the starmap.
- `p.defaultFamily = 'starsystem'`: the leaf a kind-declared page with no typed record resolves to.
- `p.matches(apiData) → boolean`: true for a location signature (`respawn_location_type`) and a record one of the leaves renders. Jump-point gates are typed `Anomaly`, a token they share with wreck sites, so the type cannot dispatch alone; a gate is recognised by an exact `Jump Point` suffix or prefix in its name. Stanton-side gates typed `JumpPoint` outright match on the token.
- `p.resolveSubtype(apiData, args) → module|nil`: a typed record decides alone. The private `recordFamily` is three-valued and the distinction is load-bearing: a string names the leaf, `false` marks a typed record no leaf models (a wreck site, a station), `nil` means no record at all. Only `nil` falls through to `|family=`, which is what stops a declared kind or a curated arg rescuing a wreck site; collapsing `false` to `nil` would silently let it. With no record a curated `|family=` names the leaf, else a kind-declared page takes `p.defaultFamily` and an undeclared page resolves nothing.
- `p.getApiConfigs() → EntityApiConfig[]`: the `locations/%s` identity endpoint.
- `p.getEditorialManifest() → table`: the kind-level Lore fields every leaf renders, `discoveredin`, `discoveredby`, `historicalnames`.

### Leaves

Two starmap bridges serve all five and are mutually exclusive: StarSystem and Body call `locationUtil.attachStarsystem` for a whole system as `apiData.starsystem`, JumpPoint and Star call `locationUtil.attachCelestialObject` for one object as `apiData.celestialobject`.

`{{Navplate system}}` builds each of its rows by intersecting `<System> system` with a type category, so that system membership is functional rather than browse taxonomy: a leaf that stops emitting either side silently empties a row. The pairs are `Stars`, `Planets`/`Moons`, `Asteroid belts` and `Jump points`.

- **StarSystem** (`p.family = 'starsystem'`): bridges by system name. Contributes the system's editorial fragment, the system-type and affiliation category trees, a collapsed "Orbital zones" section, and the Starmap footer button and metadata row JumpPoint reuses. `getTypeInfo` reads `|systemtype=`/`|type=` through `Editorial.rawArg`, because it runs ahead of editorial resolution.
- **JumpPoint** (`p.family = 'jumppoint'`): bridges by `|starmapcode=`/`|code=`. Entry and destination systems come from the page's own canonical name first, the starmap designation second. The Starmap button falls back to the raw `|starmapcode=`/`|code=` arg when the celestial fetch soft-fails, so it still renders from the arg that would have keyed it.
- **Star** (`p.family = 'star'`): one page per star, plus the black hole the starmap serves in the same shape. Shares JumpPoint's bridge, and almost every page enters through `|family=star`. The classification is the infobox subtitle, so no row repeats it, and `getCategories` resolves the spectral facet from the starmap `sub_type` before the display text, so elaborating the wording cannot move the page out of its class. Radius prefers `|radius=`, else the starmap `size` in kilometres, suppressed below 5 km (placeholders) and above the class's `maxRadiusKm`; the record's own `size` is never read.
- **Body** (`p.family = 'body'`): planets and moons in one leaf, because a moon differs from a planet only in what its parent is and every moon carries the same `Planetary Moon` sub_type. Shares StarSystem's bridge but passes the SYSTEM name explicitly, since a body's `apiData.name` is the body and the default lookup would search for a system called Hurston; it needs the whole payload because the starmap gives a parent only as a numeric `parent_id`. The body's object resolves by `|starmapcode=`/`|code=`, else by name through `locationUtil.celestialByName` restricted to `PLANET`/`SATELLITE`, the restriction mattering because a star's designation is its system's. Moon or planet is decided in five steps, each because a source contradicts itself: the record's parent type, the record's own type unless that parent is a star, `|type=`, the starmap token, then planet by default. Radius reads the record's `size` in **metres**, never the starmap's, which carries at least three different units for a body; a body with no record falls back to `|radius=` in kilometres, so the one leaf reads two units. Affiliation gets its own row because a body need not share its system's, while the chain's first tier stays the system's unconditionally since that tier links the systems category; the stored value takes the first segment only, against a single-valued column. The designation rides in the header title as an annotation rather than a row, and a parent's own page resolves with a `(planet)` qualifier where one exists. A "Sensor readings" section stores `Population rating`, `Economy rating` and `Danger rating` so a type index can column and sort them; StarSystem has no such row because a system's aggregate is almost never a real measurement.
- **Belt** (`p.family = 'belt'`): asteroid belts, clusters and planetary rings, together for the reason planets and moons are. Shares Body's bridge and its code-then-name lookup. Nothing dispatches here from a record, because the locations API's `Asteroid` rows are in-system points of interest (mining claims and bases, extraction stations, the Lagrange clusters) rather than the formations the starmap catalogues, so every page carries a curated `|family=belt|system=`. `BELT_TYPES` maps the ARK sub_types to the wiki's words, which follow the ARK in none of the three cases: `System Belt` and `System Cluster` become asteroid belt and cluster, and `Planetary Ring` files under `Planetary ring systems`, the category the ring pages carry. An object with no sub_type falls back to its bare `ASTEROID_BELT` token; every `ASTEROID_FIELD` carries a sub_type, which is why no field token is mapped. Every entry names `page = 'Asteroid formation'`, because this family has one concept page rather than the per-type index pages planets and stars have. The Distance row is the ARK's `distance` in AU, parent-relative and so comparable only between siblings; a ring reports 0 and the row disappears.

### Extending

A further leaf: `pages/module/Entity/Location/<Name>.lua` with `p.parent = 'Entity/Location'` and `p.family`, the leaf's family tag, kept equal to its `LOCATION_SUBTYPE_MAP` key (exposed as `result.family`) and to the value editors write to `|family=`. Add one `token = 'Entity/Location/<Name>'` entry to `LOCATION_SUBTYPE_MAP` in `Location.lua`, and teach `recordFamily` to return that token for the records the new leaf should claim: it is the one function `matches()` and `resolveSubtype()` both go through, so a typed record must decide there, not in the leaf. `Module:Entity/Location/testcases`'s `testSubtypeLeavesConformToChainLinkContract` iterates every entry in the map and validates it against [Module:Entity/Contract](https://starcitizen.tools/Module:Entity/Contract)'s `CHAIN_LINK` spec in strict mode, so a new leaf is covered once it is in the map, with no new test to write.

### Gotchas

- A record-less lore system (a kind-declared page with no uuid, or a uuid that never resolves) renders through the editorial fork: `apiData` resets to `{}` and the chain reruns `enrich` from `args` alone, which is how a starmap-only system still gets its bridge.
- `attachStarsystem` namespaces the starmap record as `apiData.starsystem` and never flat-merges it: the two payloads carry colliding `name`/`type`/`description`/`affiliation` keys.
- `attachCelestialObject` asks for `?include=starsystem` because that is the only reliable way to name an object's system: the starmap code's first segment is a code rather than a name, and the `starsystems` endpoint's `filter[name]` does not accept codes. The included record is compact (`id`, `code`, `name`); the zone and aggregate fields live on the full record `attachStarsystem` fetches.
- The `Jump Point` name anchors `isJumpPointRecord` matches on are case-sensitive and untrimmed on purpose: the API emits the title-case form with no trailing whitespace on every observed record, and normalising the check would loosen the gate beyond what the data shows.
