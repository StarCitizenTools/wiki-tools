# starmap

Regenerates the JSON behind `Module:Starmap/starmap.json` from the ARK Starmap
API. See [`../../README.md`](../../README.md) for how to run it; this file
covers the parts specific to this data.

## How it fetches

`/bootup` for the system roster and every jump tunnel, then
`/star-systems/{code}` per system, then `/celestial-objects/{code}` for each
planet to pick up its moons — about 417 requests, roughly two minutes at the
default pacing. Systems are fetched concurrently; output is sorted by code, so
runs are deterministic and two runs produce byte-identical files.

## Output is byte-exact

The generated bytes match the wiki page exactly, which is why `-diff` can compare
bytes rather than parsing. Two things make that true, and both are easy to break:

- Go's `encoding/json` escapes `&`, `<` and `>` as `&`, `<`, `>` —
  the same set MediaWiki's JSON content model escapes — and leaves apostrophes
  alone, as MediaWiki does.
- Go's float encoder is ECMAScript-compatible, matching the `JSON.stringify`
  output already on the page.

**Do not give `Number` a custom `MarshalJSON`.** Formatting via `strconv` with
`'g'` rewrites large values (`3458865.2579` becomes `3.4588652579e+06`) and
silently changes a megabyte of page content. There is a regression test for this.

**Struct field order defines output key order.** Reordering fields in `types.go`
rewrites the page.

## Types come from the payload, not from upstream's type declarations

The generator this replaced was TypeScript, and its `.d.ts` files are incomplete:
`ITunnelPortal` declares six fields where the API returns ten, omitting
`distance`, `latitude`, `longitude` and `type`. TypeScript passed those objects
through untouched at runtime, so the gap never mattered there — but Go structs
drop undeclared fields, so transcribing the declarations would have silently
deleted four fields from every jump-point endpoint.

If you extend the structs, check them against a live response. Note also that
objects have variable key sets: some carry `model`, `texture` or `thumbnail`.

## `aggregated_danger` is empty upstream, and cannot be derived

The field is `0` for 89 of 90 systems. The exception is Stanton at `10`, whose
row reads `population 10 / economy 10 / danger 10` while its own objects average
about 3.7 — that is hand-set, not computed.

It is emitted faithfully rather than synthesised. The previous generator wrote
`aggregated_economy` into this field, so every system's published danger reading
was really its economy reading.

Do not try to reconstruct it from per-object `sensor_danger`. That field is real
data (449 of 889 objects, range 0–10), but the system aggregates are curated
tiers, not computations: there are only 34 distinct `aggregated_economy` values
across 90 systems, with twelve sharing exactly `0.12`. Fitting candidate
aggregations against `aggregated_economy` — the one aggregate upstream does
populate, so it can be graded — matches at best 3 of 90. There is no formula to
recover.

If a system-level danger figure is ever wanted on the wiki, it has to be the
wiki's own metric, labelled as such. CIG does not publish one.

## Other quirks

- Upstream's apostrophe normalisation is partial: some descriptions still carry
  `’` (U+2019) while names use `'` (U+0027). Both are mirrored as-is.
- Subtypes named `Planetary Moon` are re-labelled to type `MOON` with a null id,
  matching the previous generator. It applies only to objects in the system
  payload, not to children fetched per planet.
