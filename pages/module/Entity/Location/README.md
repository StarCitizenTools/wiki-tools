# Module:Entity/Location

Location kind: entities backed by the game-data `/api/locations` endpoint (star systems, jump points, stars, planets and moons). Four leaves render it, StarSystem, JumpPoint, Star and Body; every other location type stays unclaimed until a leaf exists for it.

Editors never invoke this module directly; it runs inside [Template:Location](https://starcitizen.tools/Template:Location), which declares the kind, or inside [Template:Entity](https://starcitizen.tools/Template:Entity) when the page's uuid resolves to a location record the kind claims; the pipeline and the hook table are on [Module:Entity](https://starcitizen.tools/Module:Entity).

## For module editors

### API

- `p.name = 'Location'`: canonical kind name, exposed as `Data.get(args).kind`.
- `p.editorialMode = true`: a kind-declared page (`{{Location}}` injects `|kind=Location`) with no genuine record renders through the editorial fork, the entry path for lore systems that exist only in the starmap.
- `p.defaultFamily = 'starsystem'`: the leaf a kind-declared page with no typed record resolves to.
- `p.matches(apiData) → boolean`: true for a location signature (`respawn_location_type`) and a record one of the leaves renders: SolarSystem records, `Star` records, and jump-point gates. The locations API types jump-point gates as `Anomaly`, a token it shares with non-gate records (wreck sites), so the type alone can't dispatch; a gate is recognised by its name instead: an exact `Jump Point` suffix, or an exact `Jump Point ` prefix (an upstream misnaming that still names a real Pyro gate). A handful of Stanton-side gates are typed `JumpPoint` outright and match on the type token alone, with no name check.
- `p.resolveSubtype(apiData, args) → module|nil`: a typed record decides alone (its family token, or nil for a record no leaf models; a wreck site is never rescued by a declared kind or `|family=`). With no typed record, a curated `|family=` names the leaf when it maps one of the three tokens; otherwise a kind-declared page falls back to `p.defaultFamily`, and an undeclared page resolves nothing.
- `p.getApiConfigs() → EntityApiConfig[]`: the `locations/%s` identity endpoint.
- `p.getEditorialManifest() → table`: the three kind-level Lore fields every leaf renders, `discoveredin`, `discoveredby`, `historicalnames`.
- **StarSystem** (`p.family = 'starsystem'`): `enrich` bridges to the starmap by name through `locationUtil.attachStarsystem`, attaching the record as `apiData.starsystem`. `getTypeInfo` reads the system-type code from `|systemtype=`/`|type=` (the legacy arg name) through `Editorial.rawArg`, ahead of editorial resolution. Contributes its own editorial manifest fragment (size, population, star types, affiliation, system type, the object-count overrides), `getCategories` (the system-type and affiliation trees), a collapsed "Orbital zones" section (the habitable zone and frost line, which are reference astronomy with no bearing on play), and the Starmap footer button plus the Starmap-code metadata row, both read off the attached record's `code`.
- **JumpPoint** (`p.family = 'jumppoint'`): `enrich` bridges to the starmap by the editor-supplied `|starmapcode=`/`|code=` through `locationUtil.attachCelestialObject`, attaching the record as `apiData.celestialobject`. `getCategories` files the gate under its entry system's category (`<System> system`), a functional membership `{{System navplate}}` depends on, not just browse taxonomy. Also contributes the entry/destination systems, derived off the page's own canonical name first, the starmap designation as fallback. It contributes the same Starmap footer button and metadata row as StarSystem, but its accessor additionally falls back to the raw `|starmapcode=`/`|code=` arg when the celestial fetch soft-fails, so the button still renders from the arg that would have keyed it.
- **Star** (`p.family = 'star'`): one page per star, plus the one black hole the starmap serves in the same shape (Tamsa). Only three stars exist in the game, so `matches` claims little and almost every star page enters through `|family=star` with the `|code=` the legacy pages already carry. `enrich` shares JumpPoint's `locationUtil.attachCelestialObject` bridge. `getTypeInfo` makes the classification the infobox subtitle, so no row repeats it; `getCategories` adds the spectral-type facet, resolved from the starmap `sub_type` first so an editor who elaborates the display text still files under the class the data gives, plus the star's own system category, which `{{Navplate system}}` intersects with `Stars` to build its Stars row. Radius comes from the starmap `size` in kilometres, suppressed below 5 km (where the placeholders sit) and above a class's `maxRadiusKm` where the physics pins the size down, which is what stops Tanga's white dwarf rendering at 84 solar radii; the location record's own `size` is never read.
- **Body** (`p.family = 'body'`): planets and moons in one leaf, because a moon differs from a planet only in what its parent is and every moon carries the same `Planetary Moon` sub_type. `enrich` bridges through `locationUtil.attachStarsystem` like StarSystem, but passes the SYSTEM name explicitly: a body's own `apiData.name` is the body, so the default lookup would search for a system called Hurston and attach nothing. It needs the system payload rather than a per-object fetch because the starmap gives a parent only as a numeric `parent_id`, resolvable against its own system's object list. The body's own object resolves by the editor's `|starmapcode=`/`|code=` first, else by name through `locationUtil.celestialByName` restricted to `PLANET`/`SATELLITE`: a code is not derivable from a name (Hurston's is `STANTON.PLANETS.STANTONIHURSTONDYNAMICS`, built from the designation and the owning corporation) and none of the 33 in-game pages carries one, so the name is the only join, type-restricted because a star's designation is its system's. Moon or planet is decided in five steps, each because a source contradicts itself: the record's parent type, then the record's own type, then `|type=`, then the starmap token, then planet by default. A parent's own page is resolved with a `(planet)` qualifier where one exists, because a planet can share its bare name with a disambiguation page. Radius reads the record's `size` in **metres** and never the starmap's, which carries at least three different units for a body; a body with no record falls back to `|radius=` in kilometres. `getCategories` adds the type facet plus `<System> system`, which `{{Navplate system}}` intersects with `Planets`/`Moons` to build those rows. The designation rides in the header title as an annotation rather than a row, suppressed where it repeats the title. Affiliation gets its own row because a body need not share its system's, while the Location chain's first tier stays the system's unconditionally, since that tier links the systems category. The row renders an editor's own markup for free text and the canonical label otherwise, so a page saying `UEE` reads like a sibling saying nothing; the stored value is the compact form StarSystem writes, taken from the first segment because a page may name two affiliations in one arg against a single-valued column. The VerseGuide footer button derives from the system code plus the designation's tail (`STANTON/I`), limited to bodies with a game record. A "Sensor readings" section carries the starmap's own population, economy and danger figures for the body, which are also stored as `Population rating`, `Economy rating` and `Danger rating` so a type index page can column and sort them; a system's aggregate publishes a usable danger for one system in ninety, which is why StarSystem shows no such row. A short description names what a moon orbits, since the system name cannot supply it.

### Extending

A further leaf: `pages/module/Entity/Location/<Name>.lua` with `p.parent = 'Entity/Location'` and `p.family`, the leaf's family tag, kept equal to its `LOCATION_SUBTYPE_MAP` key (exposed as `result.family`) and to the value editors write to `|family=`. Add one `token = 'Entity/Location/<Name>'` entry to `LOCATION_SUBTYPE_MAP` in `Location.lua`, and teach `recordFamily` to return that token for the records the new leaf should claim, the one function `matches()` and `resolveSubtype()` both go through, so a typed record must decide there, not in the leaf. `Module:Entity/Location/testcases`'s `testSubtypeLeavesConformToChainLinkContract` iterates every entry in the map and validates it against [Module:Entity/Contract](https://starcitizen.tools/Module:Entity/Contract)'s `CHAIN_LINK` spec in strict mode, so a new leaf is covered automatically once it's in the map, no new test to write.

### Gotchas

- A record-less lore system (a kind-declared page with no uuid, or a uuid that never resolves) renders through the editorial fork: `apiData` resets to `{}` and the chain reruns `enrich` from `args` alone, which is how a starmap-only system still gets its `attachStarsystem` bridge.
- The two starmap bridges are mutually exclusive by construction: a page resolves to exactly one leaf and no leaf calls both, so it never carries both `apiData.starsystem` and `apiData.celestialobject`. JumpPoint and Star share the celestial-object bridge; StarSystem and Body share the star-system one.
- `attachStarsystem` attaches the starmap record namespaced as `apiData.starsystem`, never flat-merged into `apiData`: the two payloads carry colliding `name`/`type`/`description`/`affiliation` keys.
- `attachCelestialObject` asks for `?include=starsystem` because that is the only reliable way to name an object's system: the starmap code's first segment is a code rather than a name, and the `starsystems` endpoint's `filter[name]` does not accept codes (KYUKYA, RILA, THUSUNG and KAPARI all miss). The included record is compact (`id`, `code`, `name`); the zone and aggregate fields live on the full record `attachStarsystem` fetches.
- The `Jump Point` name anchors `isJumpPointRecord` matches on are case-sensitive and untrimmed on purpose: the API emits the title-case form with no trailing whitespace on every observed record, and normalising the check would loosen the gate beyond what the data actually shows.
